# bunium-dev

Electron-like app framework: Bun (not Node) + CEF (not Chromium-via-Electron), DOM-integrated
`<webview>` tag, Vite dev support, multi-framework boilerplate (React/Solid/Vue × TS/JS),
cross-platform packaging/signing/updates, native OS color-scheme sync, a typed IPC layer.

## Working style for this project (why it matters here specifically)

- **This is native/FFI work.** Crashes are silent segfaults with no JS stack trace. Prefer small,
  independently-runnable verification steps (a `test_*.ts` script that prints a clear pass/fail)
  over large edits before ever running anything.
- **Budget awareness.** This project's scope is large (11 phases). Break active work into
  `TaskCreate` items as you go, not all upfront. Update `PLAN.md` checkboxes when a phase
  completes — that's the persistent record across sessions, cheaper to re-read than replaying
  the conversation.
- **Never hand-roll CEF C-API vtable structs in TS.** Always go through the C++ shim
  (`native/mac/bunium_common.h` + `bunium_shim.cpp` + `bunium_window_mac.mm`) with a flat C ABI.
  Extend the shim's ABI surface (add a new `extern "C"` function, remember `BUNIUM_EXPORT`) rather
  than trying to reach raw CEF structs from `bun:ffi`. The JS-facing package lives in `src/`
  (`native.ts` binds the ABI, `window.ts` is the public `BuniumWindow` class) — extend that, not
  ad-hoc `dlopen` calls in scripts.
- **Every new exported shim function needs `BUNIUM_EXPORT`** (`__attribute__((visibility("default")))`)
  or `bun:ffi`'s `dlopen` will fail to find it silently at the JS layer, not the compile layer.
- **Never give a native ABI function more than 8 arguments.** Empirically found a `bun:ffi`
  arm64 issue where the 9th+ argument silently corrupts (see `ARCHITECTURE.md` §18). Split into
  multiple calls or pack values into a buffer instead.
- **`FFIType.cstring` is unsafe for anything that can return `NULL`** — it comes back as a truthy
  `CString` object wrapper even when null, breaking `if (!x) break` drain loops (silent infinite
  loop, not a crash — see `ARCHITECTURE.md` §15). Use `FFIType.ptr` + explicit `=== null` check
  instead, constructing `new CString(ptr)` only when non-null.
- **macOS is the only platform validated so far.** Don't assume findings (subprocess model,
  resource paths, framework load path) transfer to Linux/Windows — those need their own
  validation pass per `PLAN.md` Phase 6/7.
- **Don't add a bespoke IPC bridge per feature.** `window.__bunium.reportBounds()` (Phase 2) was
  deliberately a one-off to prove the mechanism, not a pattern to repeat. Before wiring up
  draggable regions, webview control messages, or any Phase 5 system-API callback, check `PLAN.md`
  for the typed-IPC-layer standing requirement — build/extend that instead of another
  `CefV8Handler`/`CefProcessMessage` pair. `<bunium-webview>` (Phase 2) follows this: it reuses the
  generic `window.__bunium.send()` channel with 4 reserved message names, no new ABI/message type.
- **The injected-JS bootstrap in `bunium_common.h` is one big C-string-literal concatenation
  (`frame->ExecuteJavaScript(...)`, `OnContextCreated`) — appending to it is error-prone.** A real
  bug hit while adding `<bunium-webview>`: tacking a new `#define ..._JS` macro onto the tail of
  the existing literal silently dropped that literal's own closing braces/parens, breaking the
  _entire_ bootstrap (including unrelated, previously-working code) with a parse error only
  visible via `OnConsoleMessage`'s forwarded stderr, not at C++ compile time or `tsc --noEmit`.
  **After editing this block, always run a real example script and check stderr for `[console]
... SyntaxError`, don't just confirm the native build and TS typecheck succeeded** — neither
  catches string-concatenation logic bugs here.
- **Never commit with any Claude/AI co-authorship attribution** — this is a global rule (see
  user's `~/.claude/CLAUDE.md`) the user re-emphasized specifically for this project. No
  `Co-Authored-By: Claude`, no "generated by" tags, nothing, ever.
- **Keep this skill file (and `PLAN.md`/`ARCHITECTURE.md`) updated as features land**, not just
  at big milestones — a skill file that's drifted from what the code actually does is worse than
  no skill file, because it actively misleads the next session.
- **Bun version:** always keep on latest (`bun upgrade`), don't pin defensively. bunium only
  depends on Bun's public JS API surface (`bun:ffi`, `Bun.*`), so internal runtime changes
  shouldn't matter unless that public API itself changes.
- **Phase 5 system surface lives in `src/system/` + `native/mac/`** (menu/tray in
  `bunium_system_mac.mm`, notifications in `bunium_system_notify_mac.mm`, dialogs in
  `bunium_system_dialogs_mac.mm`), sharing one app-level event drain: native pushes into a
  mutex-guarded inbox via `PushSystemEvent` (`native/mac/bunium_system_events.h`, defined in
  `bunium_system_mac.mm`) and `bunium_poll_system_event()` (same envelope JSON as
  `bunium_poll_message`) is drained by the app pump via `systemEvents.drain()`
  (`src/system/events.ts`). Every new system feature reuses that bus — never a second
  native->JS path. New system ABI symbols are exported from the owning `.mm` (add the file +
  symbol to `build.sh` and `src/native.ts`). Menu clicks route through a single shared
  `BuniumMenuDispatcher` identified by `NSMenuItem.tag`; notification clicks and dialog
  results ride the same bus (`bunium-notification-click`, `bunium-dialog-result`).
- **Notifications backends, chosen per-process by bundle presence:** `UNUserNotificationCenter`
  only when the process has a bundle identifier — referencing it from an unbundled dev
  process throws `NSInternalInconsistencyException` and previously crashed the whole Bun
  runtime, so the unbundled path uses the deprecated-but-functional `NSUserNotification`
  (deliver via `deliverNotification:`, id rides in `userInfo["buniumId"]`, clicks via
  `didActivateNotification:`). Dialogs are completion-handler driven
  (`beginWithCompletionHandler:` / `beginSheetModalForWindow:`) so they never block the JS
  results arrive as events keyed by requestId, resolved into promises in
  `src/system/dialogs.ts`.
- **Tray details:** title rendering uses `item.button.title` (never the deprecated
  `NSStatusItem.title` property), icons via `button.image` (file path `setIcon`, or SF Symbol
  `setSymbol`), and menu-less tray clicks via an opt-in `Tray.onClick` that wires the status
  button target/action to the shared dispatcher (button tag = tray handle; `trayClicked:`
  pushes `bunium-tray-click {"id":T}`). `setMenu()` supersedes click delivery. bun's ffi
  `Pointer` has no numeric accessor, so tray identity is read back through
  `bunium_system_tray_get_id`. Gotcha: toggling `template` on an NSImage in a .mm TU must use
  `[image setTemplate:]` -- `image.template` dot-syntax fails to parse (`template` is a C++
  keyword).
- **Never run two example scripts simultaneously.** CEF's per-profile `ProcessSingleton`
  (default `root_cache_path` = shared `~/Library/Application Support/CEF/User Data`) aborts
  the second concurrent process with "Aborting now to avoid profile corruption" (exit 21).
  Test scripts must run sequentially; parallel shells are fine. Real apps get a per-app
  `root_cache_path` at packaging time (Phase 8).

## Phase 6 — Linux port (full examples/ sweep green, 2026-08-22)

- **Dev/build/test is Docker-only** (`docker/linux/`) since this session's host is macOS, no
  native Linux desktop available. `Dockerfile` = arm64 Ubuntu 24.04 (matches Docker Desktop's
  native platform on Apple Silicon, avoids QEMU) with the clang/cmake/X11-dev/Chromium-runtime-
  dep/Xvfb toolchain. `fetch-cef.sh` downloads the pinned CEF linuxarm64/linux64 distro (10MB
  chunks -- this network path caps a single response at 10MB) + builds `libcef_dll_wrapper` via
  cmake/ninja. `run-examples.sh` runs every `examples/*.ts` sequentially under Xvfb (same
  ProcessSingleton one-at-a-time rule as every other platform) with a PASS/FAIL summary. Build:
  `docker build -t bunium-linux-dev -f docker/linux/Dockerfile .` then
  `docker run --rm -v "$(pwd)":/work -w /work bunium-linux-dev bash docker/linux/fetch-cef.sh`
  then `... bash native/linux/build.sh` then `... -e LD_LIBRARY_PATH=/work/native/build ...
  bash docker/linux/run-examples.sh`.
- **`native/linux/build.sh` builds with g++, not clang++.** CEF's own cmake-built
  `libcef_dll_wrapper.a` on this Ubuntu image resolves to g++; linking a clang++-compiled
  `bunium_shim.cpp` against it segfaulted immediately inside `CefInitialize` (confirmed via gdb:
  a by-value `scoped_refptr<CefApp>` parameter's hidden-reference pointer arrived null/garbage)
  -- a cross-compiler C++ ABI mismatch, not a bunium logic bug. Same failure class as the
  Windows port's bootstrap-flag mismatch (wrapper and linking code must share one toolchain),
  different root cause here (compiler vendor, not a CEF build define).
  `native/mac/bunium_shim.cpp`/`subprocess_main.cpp`/`bunium_bsdiff_wrap.mm` compile unchanged
  (already proven platform-agnostic by Windows); only `bunium_window_linux.cc` (real Xlib
  window + sublayers, XPutImage software blit, X11 Shape extension for sublayer clipping, no
  DPI scaling yet) and `bunium_system_linux_stub.cc` (honest no-op Phase 5 stubs -- tray/menu/
  notify/dialogs not ported yet) are Linux-specific.
- **Chrome-runtime pak/locale files resolve relative to libcef.so's own directory
  (`base::PathService::Get(base::DIR_MODULE)`/dladdr), NOT via `CefSettings.resources_dir_path`
  -- a real startup-crashing bug, root-caused via gdb+strace.** Every window-creating example
  hard-crashed with a release `CHECK` (SIGTRAP, silent -- no stderr message) inside
  `ChromeMainDelegate::PostEarlyInitialization -> LoadLocalState`. `resources_dir_path` only
  governs CEF's own resource-bundle delegate; Chrome-runtime's separate resource-bundle init
  looks for `chrome_100_percent.pak`/`chrome_200_percent.pak`/`resources.pak`/locale paks next
  to libcef.so itself. Fixed in `native/linux/build.sh`: copy `*.pak` + `locales/` from
  `vendor/cef-<platform>/Resources/` next to the built shim -- `native/win/build.sh` already
  did this (for the same reason, just not previously recognized as the same root cause).
  `icudtl.dat`/`v8_context_snapshot.bin` need the same DIR_MODULE-relative copy (ICU/V8 init).
  **Any future platform port hitting a silent SIGTRAP/CHECK crash on Chrome-runtime startup
  should check this first** -- it won't show up in stderr, only via gdb backtrace or strace.
- **`src/paths.ts` needs an explicit Linux branch -- it silently fell through to the macOS
  `.dylib` path otherwise** (`ERR_DLOPEN_FAILED: invalid ELF header`). Fixed:
  `native/build/bunium_shim.so` dev-tree path, Windows-style flat Release/Resources CEF layout
  (no framework bundle on Linux either), arch-derived `vendor/cef-linuxarm64`/`cef-linux64` dir
  matching `native/linux/build.sh`'s own convention, plus a `bunium-linux-<arch>` platform-
  package branch for Phase 11 parity.
- **35/37 examples PASS** (2026-08-22, linuxarm64, bun 1.4.0) -- every window/IPC/webview/
  system-stub/update example green. Two non-bugs: `color-scheme-live-test.ts` is inherently
  mac-only (`defaults`/`osascript`), stays off the run matrix same as it already does for
  Windows. `vite-dev-test.ts` failed once on a stone-cold container (`bunx vite`'s first-ever
  invocation resolves ~110 packages, blowing the test's 10s ready-timeout) but passed cleanly
  once `bunx`'s cache was warm -- not a bunium bug.
- **v1 scope gaps, deliberate** (matches "repeat Phase 0-1, not full parity" plan note): X11
  only (no Wayland); no DPI/HiDPI scaling; no native context-menu suppression (mac's
  `OnBeforeContextMenu` right-click-crash fix from this same session not ported -- unconfirmed
  whether Linux has the same crash, worth checking); Phase 5 system surface is stub-only;
  no synthetic resize-edge/draggable-region hit-testing for frameless windows; sublayers paint
  opaque only (no alpha compositing, needs a real compositor); no packaging/distribution
  mechanism yet (`docker/linux/` is dev/test only).

## Phase 8 — macOS packaging (verified working 2026-08-17)

- **Package:** `bun run pack:mac -a <app-dir> -n Name -i com.example.id [-o out] [--no-dmg]`
  (script is `packaging/mac/package.sh`; pass args directly, no `--` separator). Produces
  `dist-app/Name.app` (launcher + bundled bun + CEF framework + shim/subprocess with
  `@loader_path`-rewritten install names + ANGLE libs + app files + materialized
  `node_modules/bunium`) + ad-hoc codesign + DMG. `src/native.ts` resolves every native
  path from `BUNIUM_SHIM_PATH`/`BUNIUM_SUBPROCESS_PATH`/`BUNIUM_FRAMEWORK_DIR` env overrides
  (launcher exports them) so dev/packaged share one code path.
- **macOS helper apps are required and easy to miss.** When the main app is bundled,
  Chromium spawns the renderer + alerts utility via sibling per-type bundles named
  `<subprocess-basename> (<Type>).app` (e.g. `bunium_subprocess (Renderer).app`), NOT the
  plain subprocess path. Missing helpers = silent posix_spawnp ENOENT (release DLOG is a
  no-op) = renderer never starts = navigation dies with ERR_ABORTED and a blank/white
  frame. Symptoms to recognize: only gpu/network/storage subprocesses exist (`ps` shows no
  `--type=renderer`), no renderer crash report, no console output from the page.
  Constraints when building them: (1) helper `CFBundleIdentifier` MUST equal the main
  app's — the child self-derives its MachPortRendezvous lookup name
  (`<bundle-id>.MachPortRendezvousServer.<browser-pid>`) from its own bundle id and there
  is no base-bundle-id propagation; a suffixed id yields a 1102 crash loop. (2)
  `install_name_tool`/otool-classic can't open paths whose final component has spaces —
  rewrite a no-space temp copy then `mv` it into place.
- **Debug env vars** (all gated, safe to leave on): `BUNIUM_BUNDLE_DEBUG` (mainBundle
  identity dumps), `BUNIUM_CEF_VERBOSE` (CEF INFO logs + `[paint]`/`[load-*]`/`[scheme-*]`
   - renderer `[context-created]`), `BUNIUM_CEF_SWITCHES` (inject browser switches — the
     real argv is `bun <script>` so Chromium never parses post-script args as switches).
- **posix_spawn interposer** (`packaging/mac/spawn_interpose.mm`): build with `clang
-dynamiclib -lc++`, load via `DYLD_INSERT_LIBRARIES` — but only when launching bun
  DIRECTLY (a `#!/bin/sh` launcher strips `DYLD_*` env). Must use the `__DATA,__interpose`
  section with link-time `&posix_spawn` for the real pointer: plain exported symbols don't
  interpose in modern dyld, and `dlsym(RTLD_NEXT)` inside the wrapper deadlocks or
  recurses in bun's spawn path. Logging must be raw `write(2)` — stdio locks deadlock
  inside spawn.
- **Frame-count gotcha (BigInt):** `win.frameCount` is a `u64` FFI return — compare via
  `< 1` not `=== 0`. And the first OnPaint can be the pre-paint white surface (cold
  profile after packaging) — the verifier must poll screenshots until the expected pixels
  appear, not accept frame #1.

## Phase 9 — auto-update (verified working 2026-08-17)

- **Delta patches via vendored bsdiff** in `vendor/bsdiff/` (from mendsley, BSD-2-Clause; the
  `.gitignore` has a negation so this small subtree stays tracked while CEF stays ignored).
  Compiled as C objects (`bsdiff.o`/`bspatch.o`) in `native/mac/build.sh` — C, not C++, because
  the sources use implicit `void*` conversions; the `BSDIFF_EXECUTABLE`/`BSPATCH_EXECUTABLE`
  paths pull in bzlib and are never defined. The shim bridge `native/mac/bunium_bsdiff_wrap.mm`
  exports `bunium_bsdiff`/`bunium_bspatch`/`bunium_bsdiff_patch_info` (≤3 args, file paths in /
  out, status codes 0 / -1 file / -2 bad header / -3 algorithm / -4 OOM); bindings in
  `src/native.ts`, typed wrapper in `src/bsdiff.ts`.
- **The 24-byte header is the wrapper's job.** mendsley's `bsdiff()`/`bspatch()` do NOT write or
  parse the `ENDSLEY/BSDIFF43` magic + 8-byte LE new-size header (upstream keeps it in its
  executable `main()`s) — the wrapper writes it on diff and validates it on patch/
  `patch_info`. Also: the vendored headers name a parameter `new` (C++ keyword), so the wrap
  file does `#define new new_data_param` around the include; and the stream `write` callback
  contract is **return 0 on success** (returning bytes written makes upstream `writedata` see a
  non-zero and fail).
- **Deterministic tar layer** `src/tar.ts` (ustar): sorted entries (dirs first by `0`/`1` +
  path key), mtime 0, uid/gid 0, fixed modes, POSIX paths, two zero-block terminator. `bun
src/tar.ts <dir>` prints an archive to stdout; `collectDirectory` walks a tree into entries.
  Determinism verified (identical sha256 across runs) — it's what makes build-side and
  client-side tars byte-equal so patches apply.
- **`src/update.ts`** — `updater.check()` fetches `<channel>-<os>-<arch>-update.json`;
  `install()` prefers `patch.bsdiff` only when `currentVersion == fromVersion`, else
  `full.tar.zst`. Patch path re-tars the installed tree with the same deterministic writer,
  validates the patch header output-size against `manifest.fullSize` and sha256, then
  stage-writes to a sibling staging dir and rename-swaps (backup restored on failure). CEF is
  never touched (independently-versioned artifact by design). Typed event emitter
  (`checking`/`downloadStarted`/`progress`/`applying`/`ready`/`relaunching`/`error`, all
  discriminated unions). `Bun.zstdCompressSync`/`Bun.zstdDecompressSync` for the transport
  layer; the bsdiff patch itself is uncompressed.
- **Release CLI** `bun run release:update --name X --channel stable --platform mac --arch arm64
--version 1.0.2 --from-version 1.0.1 --old <prev-dist> --new <cur-dist> --out <dir>`
  (`scripts/release.ts`) emits `{update.json,patch.bsdiff,full.tar.zst}`. Two runs byte-
  identical (verified).
- **Verification:** `examples/bsdiff-test.ts` (round-trip + corrupt/truncated header
  rejection, headless) and `examples/update-e2e-test.ts` (in-process static host; patch path,
   > 1-behind full fallback, up-to-date, corrupt-patch recoverable failure leaving the install
   > untouched). Both exit 0=PASS; run sequentially like all examples.
- **Packaged-app restart (wired 2026-08-18):** `src/relaunch.ts` — `relaunchApp()`, the
  ready-to-use handler for `updater.relaunch(relaunchApp)`: shuts down CEF then re-execs
  the same `process.execPath` + `process.argv[1..]` the packaged launcher ran (zero launcher
  changes). Detached `sh` shim waits for the parent PID to die before `exec` (CEF
  ProcessSingleton aborts a concurrent second browser). Gotcha baked into
  `buildRelaunchCommand`: `sleep` takes SECONDS — the ms poll interval is passed as
  fractional seconds (`toFixed(3)`). `updater.relaunch(handler)` threads the installed dir
  through to the handler + `relaunching` event. All updater/relaunch symbols are exported
  from `src/index.ts`. Verified via `examples/relaunch-test.ts` (headless); the real
  packaged quit-relaunch still needs a desktop.
- **Swap-crash self-repair (2026-08-18):** `swap()` journals the in-progress
  two-rename swap to `<installDir>.updating` (JSON: `{"staging": <path>}`)
  before the first rename and removes it on success/failure-cleanup.
  `repairInterruptedUpdate(installDir)` (exported from `src/index.ts`, also
  called at the top of every `install()`) resolves all crash windows: staged
  tree present → roll forward (drops old backup), staging lost + backup
  present + install missing → roll back, install live → finish cleanup;
  corrupt journal falls back to backup semantics. Apps should call it once at
  startup before their first `check()`. Verified across all six states
  (`examples/update-journal-test.ts`, headless; e2e + relaunch tests still
  PASS).

## Phase 11 — npm publish path (resolution + staging verified; license + CI landed 2026-08-18)

- **Artifact resolution is in `src/paths.ts`** (native.ts re-exports it). Per key:
  env override (`BUNIUM_SHIM_PATH`/`BUNIUM_SUBPROCESS_PATH`/`BUNIUM_FRAMEWORK_DIR`,
  the packaged-app launcher mode) → dev tree (existence check) → platform package
  `bunium-<platform>-<arch>` via `import.meta.resolve` in the consumer's node_modules.
  `BUNIUM_NATIVE_PACKAGE` overrides the package name (testing). Dev behavior is
  byte-identical (dev paths win when present); the platform fallback only fires when
  neither env nor dev tree is available.
- **Platform-package layout** (what `dist-release/bunium-darwin-arm64/` looks like):
  `shim/{bunium_shim.dylib, bunium_subprocess, ANGLE libs+json}` +
  `framework/Chromium Embedded Framework.framework/` (trimmed). Shim + subprocess
  CEF install name = `@loader_path/../framework/...` (location-independent; the old
  absolute dev path never ships). ANGLE needs no rewrite — its rpaths
  (`@executable_path/`) resolve against the subprocess's own dir.
- **`bun run release:artifacts`** = `scripts/stage-release-artifacts.sh`: builds/stages
  the platform package + `bunium-darwin-arm64-<v>.tar.gz` under `dist-release/`. Needs
  `native/build/` + `vendor/` (git-ignored, local only). ~260M staged.
- **`scripts/verify-platform-package.sh`** = the installed-consumer harness: rebuilds
  `dist-release/_consumer/` (materialized bunium + platform package, no dev tree on the
  resolution path) and runs a real window + paint (green-pixel check). Run it after any
  change to `src/paths.ts` or the staging script.
- **Verification gotcha (same class as the `FFIType.cstring` one):** the resolution
  bug you'd get from a wrong layout is a dlopen/load failure at window creation, NOT a
  JS error — always run the consumer harness, not just `tsc --noEmit`.
- **CI release pipeline** = `.github/workflows/release.yml` (tag `v*`, macos-14
  arm64): downloads the vendored CEF distro fresh (`cef_binary_<version>_macosarm64_minimal.tar.bz2`,
  sha1-pinned via `CEF_SHA1` env), builds `libcef_dll_wrapper` (cmake), then
  `build:native:mac` → `release:artifacts` → `verify-platform-package.sh`, attaches
  the archive to a GitHub Release. CEF URL gotcha: the old
  `downloads/cef_binaries/<version>/` prefix 404s (index.json URLs are stale); flat
  `https://cef-builds.spotifycdn.com/cef_binary_<version>_macosarm64_minimal.tar.bz2`
  works and serves the pinned sha1. Bump `CEF_VERSION`/`CEF_SHA1` (index.json value)
  together when upgrading `vendor/`.
- **Still open:** npm publish (needs credentials; `private` must come off, platform
  package added as `optionalDependency` at publish; tag `v0.0.1` first to exercise

## Rebuild commands (macOS)

Run `bun run build:native:mac` (or `native/mac/build.sh` directly) — it builds
`native/build/bunium_shim.dylib` + `native/build/bunium_subprocess` from `native/mac/*.{cpp,mm}`
against `vendor/cef-macosarm64/`, including the `install_name_tool` framework-path fix (see
`ARCHITECTURE.md` §5). Requires `vendor/cef-macosarm64/build/libcef_dll_wrapper/libcef_dll_wrapper.a`
to exist first — build once via
`cmake -S vendor/cef-macosarm64 -B vendor/cef-macosarm64/build && cmake --build vendor/cef-macosarm64/build --target libcef_dll_wrapper`.
